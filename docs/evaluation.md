# Evaluation

All numbers in this repository come from files written by the scripts below. Nothing is typed by hand: the README tables are regenerated by `scripts/update_readme_results.py`, and the UI's Experiments page reads the same files through `GET /experiments`.

## Official AppsRetrieval (CoIR) with MTEB

```bash
python evaluate.py --config configs/baseline_dense.yaml --mode dense  --output appsretrieval_results.json
python evaluate.py --config configs/p0_apps.yaml                      --output artifacts/eval/appsretrieval_p0.json
```

| Mode | MTEB model object | Who ranks the corpus |
|---|---|---|
| `dense` | `PrePostPipelineEncoder`, an `mteb.models.abs_encoder.AbsEncoder` (the organisers' template): query preprocessing, then the configured code embedder with its documented prompts, then L2 normalization | MTEB (cosine) |
| `hybrid` | `CodeFusionSearchModel`, which also implements `mteb.models.SearchProtocol` (`index` / `search`) | CodeFusion: dense + BM25 + symbols + fusion (+ reranker, graph and structural scoring per config) |

Both run through `mteb.evaluate(model, [mteb.get_task("AppsRetrieval")])`. The result file is MTEB's own `TaskResult.to_disk(...)` output. Next to it, `*_summary.json` records:

* NDCG@1/5/10/100, MRR@1/5/10/100, Recall@10/100 and MAP@10 (copied from MTEB's scores)
* model load, evaluation and total time; peak RSS
* embedding cache statistics and encode seconds
* hybrid only: parse, index and query-encode stage times, plus per-query search latency P50/P95/mean
* the enabled components and the full resolved config

**Hybrid ranking fidelity.** MTEB re-sorts the returned `{doc_id: score}` maps. `CodeFusionSearchModel.search` therefore emits strictly decreasing scores (`n - rank + ε·score`), so MTEB scores exactly CodeFusion's order.

**Shared cache.** Both paths encode byte-identical texts: MTEB's `_corpus_to_dict` text equals CodeFusion's document text, verified on a 300-document sample with 0 mismatches. Queries are passed through unchanged. The corpus is therefore encoded once, and the hybrid evaluation, ablations and benchmark reuse those vectors from `artifacts/cache/embeddings.sqlite`.

**CPU cost.** jina-code-embeddings-0.5b on 4 physical cores (fp32, `torch_threads: 4`, 1024-token limit) encodes roughly 0.3 queries/s and 0.6 documents/s. The full test split (3,765 queries, 8,765 documents) takes several hours. Encoding commits to the cache every 256 texts, so an interrupted run resumes where it stopped.

**Smoke tests.** `--max-queries/--max-corpus` build a seeded subsample: the sampled queries, all their positives, and random distractors. The output file name always contains `subset_q…_c…` and never overwrites the official file.

## Metrics

`evaluation/metrics.py` implements NDCG@k (graded gains `2^rel − 1`), MRR@k and Recall@k with pytrec_eval semantics. The ablation runner uses these on CodeFusion's own rankings. Ablation A (dense only) must reproduce the official MTEB dense score, and the runner stores the official reference next to the table so the check is visible.

## Ablations

```bash
python scripts/run_ablations.py --list
python scripts/run_ablations.py --config configs/full.yaml                                    # full split
python scripts/run_ablations.py --config configs/full.yaml --only A D G H --max-queries 300 --max-corpus 3000
```

| Exp | Adds | Config delta (see `--list` for exact overrides) |
|---|---|---|
| A | dense only | everything else off, `fusion.method=dense_only` |
| B | BM25 only | plain tokenization, raw field |
| C | dense + BM25 | min-max score fusion |
| D | dense + BM25 + RRF | `rrf_k=60`, equal weights |
| D2 | dense-weighted RRF | BM25 weight 0.3 |
| E | identifier preprocessing | camel/snake splitting and stemming in BM25 |
| F | structural representation | BM25F over raw, structural, context and docstring |
| G | symbol retrieval | symbol index in the fusion |
| H | reranker | cross-encoder over the fused top-30 |
| I | code graph | 1-hop expansion + structural scoring |
| J | query-adaptive weighting | intent multipliers |
| K | full system | + diversity, expansion, versions |
| L | diversity / MMR | MMR λ 0.75 |
| M | late interaction | MaxSim rerank (needs per-token corpus encodings, see below) |
| N | Joern / CPG | needs Joern |

Output: `artifacts/ablations/ablations_<dataset>.{json,csv,md}`, with experiment, NDCG@10, MRR@10, Recall@100, P50/P95 per-query search latency, indexing time, model, enabled components and status. The JSON also has per-stage index times and the number of embeddings computed. Rows that cannot run carry `NOT RUN: <reason>` and no metrics.

**Latency definition.** P50/P95 cover the engine's per-query search: retrievers, fusion, graph, reranking, structural scoring and diversity. Query embeddings are computed in one batch beforehand (as MTEB does). Single-query embedding latency is measured separately by the embedding benchmark.

**P0 selection.** `scripts/select_p0_config.py` writes `configs/p0_apps.yaml` from the best full-split ablation row (NDCG@10, then MRR@10, then latency). A component that did not improve AppsRetrieval is therefore not part of the P0 configuration. It stays available in `full.yaml` for repository search, P1 and the demo, where structure matters. AppsRetrieval queries are competitive-programming problem statements, and the documents are standalone solutions without meaningful identifiers or call graphs. Symbol and graph signals are expected to matter far more on real repositories than on this benchmark; the ablation measures this instead of assuming it.

## Embedding benchmark

```bash
python scripts/benchmark_embeddings.py --max-queries 100 --max-corpus 500
python scripts/benchmark_embeddings.py --models jina-code-0.5b --full
```

For each model, the benchmark records NDCG@10, MRR@10 and Recall@100 (dense only, FAISS flat), indexing time and docs/s for the documents actually encoded, online query latency P50/P95 (one query at a time: embedding + search, uncached), RAM growth after loading, and peak VRAM on CUDA. A model that cannot be downloaded or loaded is written as `NOT RUN: <error>` and the others continue.

## Reproducing everything

```bash
python scripts/run_experiment_suite.py            # official → ablations → reranker → p0 → embeddings → versioning
python scripts/update_readme_results.py
```

The suite is resumable (completed steps are skipped) and logs to `artifacts/eval/logs/suite*.log`.

## MLflow

Set `tracking.mlflow: true` (and optionally `tracking.tracking_uri`) in a config. `evaluate.py`, the ablation runner and the benchmarks then log the flattened config, model, NDCG@10, MRR@10, latencies, indexing time and the enabled components. With tracking disabled or MLflow missing, logging is a no-op.

## Experimental modules

**Late interaction** (`experimental/late_interaction.py`). `LateInteractionRetriever` implements ColBERT-style MaxSim, `score(q, d) = Σ_t max_u cos(E_t, E_u)`, over per-token embeddings from any Hugging Face encoder (`TransformerTokenEncoder`) or a hashing encoder for tests. It can search a small corpus exhaustively or rerank a candidate list, behind the same interface as single-vector retrieval. Ablation M is **not run** on AppsRetrieval: per-token document encodings for 8,765 documents would need another multi-hour CPU encoding pass and several GB of float16 token vectors. The module is unit-tested (`tests/test_experimental.py`), and no benefit is claimed.

**Joern / CPG** (`experimental/joern.py`, `scripts/joern_enrich.py`). Install Joern (Java 17+):

```bash
curl -L https://github.com/joernio/joern/releases/latest/download/joern-install.sh | sh
python scripts/index_repo.py examples/sample_repo
python scripts/joern_enrich.py examples/sample_repo --index-dir artifacts/index
```

The Joern script exports each method's span, resolved callees and parameter-to-call-argument data-flow reachability. CodeFusion maps these onto snippets by file and line overlap, adds CALLS edges the AST pass missed, and stores data-flow evidence. Without Joern, the script and ablation N report NOT RUN. AppsRetrieval documents are single-file solutions, where a CPG adds little over the AST call graph, so this experiment targets repository search. No improvement is claimed until measured.

**SCIP.** `symbols.scip_index: path/to/index.scip` merges precise cross-file occurrences into the symbol index when the `scip` CLI is available. It is optional and skipped silently otherwise.
